## 1. 产品概述

### 1.1 产品定义

AICK-MMP (AI Camera Kit - Multi-region Monitoring Platform) 是一款面向企业的多区域分布式视频监控管理平台,采用现代微服务架构,支持大规模跨地域摄像头统一管理、实时视频流低延迟传输和边缘计算智能运维。

### 1.2 产品背景

随着安防监控需求的不断增长,企业在多地域部署摄像头监控系统时面临以下痛点:
- **分散管理困难**: 不同区域的摄像头各自为政,缺乏统一管理平台
- **传输延迟高**: 传统监控方案视频流延迟超过2秒,无法满足实时监控需求
- **带宽成本高**: 所有视频流传输到中心服务器,网络带宽成本高昂
- **运维复杂**: 设备故障检测依赖人工,响应时间长
- **扩展性差**: 系统难以支持大规模设备接入

AICK-MMP旨在通过边缘计算、WebRTC低延迟传输、智能运维等技术,解决上述问题。

### 1.3 产品目标

#### 1.3.1 短期目标 (MVP版本)
- 支持100+摄像头统一管理
- 实现WebRTC实时视频流传输,延迟<200ms
- 支持边缘节点本地视频预处理
- 完成核心功能模块开发并上线

#### 1.3.2 中期目标 (V1.0版本)
- 支持1000+摄像头同时在线
- 支持10+边缘节点分布式部署
- 实现智能故障检测和自动告警
- 完善移动端支持

#### 1.3.3 长期目标 (V2.0版本)
- 支持10000+摄像头大规模部署
- 引入AI智能分析功能(行为识别、异常检测)
- 实现云边协同架构
- 开放API接口支持第三方集成

#### 1.5.3 ROI分析

**场景: 连锁零售企业200家门店,200个摄像头**

**投入成本**:
- 系统部署费用: 50万元
- 年度维护费用: 10万元/年
- 培训成本: 5万元
- **合计: 60万元/年**

**业务收益**:
- 节省运维人力: 4人×20万/人/年 = 80万/年
- 降低网络成本: 15万/年
- 提升管理效率带来的收益: 20万/年
- 减少故障损失: 10万/年
- **合计: 125万/年**

**投资回报率**:
```
ROI = (收益 - 投入) / 投入 × 100%
    = (125 - 60) / 60 × 100%
    = 108%
```

**投资回收期**:
```
回收期 = 年投入 / 年收益 × 12个月
       = 60 / 125 × 12
       ≈ 5.8个月
```

**净现值(NPV,3年期)**:
```
NPV = -60 + (125-60)/(1+0.1)^1 + (125-60)/(1+0.1)^2 + (125-60)/(1+0.1)^3
    = -60 + 59.1 + 53.7 + 48.8
    = 101.6万元
```

## 2. 市场与用户分析

### 2.1 用户画像

#### 用户画像1: 系统管理员 - 张经理
- **基本信息**: 35岁,IT部门经理,某连锁零售企业
- **背景**: 负责公司200家门店的IT运维工作
- **痛点**: 
  - 各门店摄像头独立管理,运维成本高
  - 无法实时查看所有门店的监控画面
  - 故障响应慢,需要逐个排查
- **期望**: 能够在一个平台上统一管理所有门店的摄像头,实时查看监控画面,快速定位故障

#### 用户画像2: 操作员 - 李安全
- **基本信息**: 28岁,安保专员,某工业园区
- **背景**: 负责园区内50个监控摄像头的日常管理
- **痛点**:
  - 需要频繁切换查看不同区域的摄像头
  - 视频延迟高,无法及时发现问题
  - 录像查找和回放操作复杂
- **期望**: 能够同时查看多个摄像头画面,视频流延迟低,录像查找便捷

### 2.2 使用场景

#### 场景1: 门店远程巡检
**用户**: 连锁零售店长
**背景**: 店长需要定期检查门店营业状况
**流程**:
1. 登录系统,选择需要巡检的门店
2. 查看门店实时监控画面
3. 发现异常(如货架混乱、人员聚集)进行截图或录像
4. 下达整改指令

**需求**: 视频流延迟低、画面清晰、多区域快速切换、支持截图和录像

#### 场景2: 故障排查与维修
**用户**: IT运维人员
**背景**: 某摄像头突然离线,需要快速定位问题
**流程**:
1. 系统自动告警,通知运维人员
2. 在告警列表中查看详细信息
3. 检查摄像头状态和网络连接
4. 远程重启摄像头或派遣现场维修
5. 维修完成后恢复正常,记录维修日志

**需求**: 实时告警、故障定位准确、远程控制、操作日志记录

#### 场景3: 历史录像回放
**用户**: 安保主管
**背景**: 发生安全事故,需要调取录像进行调查
**流程**:
1. 选择发生事故的时间范围和摄像头
2. 查询该时间段内的录像列表
3. 在线回放录像,定位关键画面
4. 下载录像作为证据
5. 生成事故报告

**需求**: 录像快速检索、在线流畅回放、下载速度快、支持时间轴定位

#### 场景4: 应急指挥调度
**用户**: 安保指挥员
**背景**: 突发紧急事件(如火灾、入侵),需要实时监控现场
**流程**:
1. 接收告警信息
2. 快速打开相关摄像头的实时画面
3. 同时监控多个区域画面
4. 发现异常及时调度安保人员
5. 全程录像留存

**需求**: 快速响应、多画面同屏显示、画面清晰稳定、录像可靠

### 3.2 用户认证与权限管理 (M1)

#### 3.2.1 用户登录

**功能描述**: 支持用户通过用户名/密码登录系统,使用JWT Token进行身份验证。

**用户故事**: 
> 作为系统管理员,我希望能够使用安全的登录方式访问系统,以确保系统数据的安全性。

**功能需求**:
1. **登录界面**
   - 用户名输入框,支持回车键提交
   - 密码输入框,支持密码可见性切换
   - "记住我"复选框,勾选后下次自动填充用户名
   - 登录按钮,支持Loading状态
   - 显示默认账号提示(admin/admin123)

2. **登录验证**
   - 验证用户名和密码是否为空
   - 验证用户名是否存在
   - 验证密码是否正确
   - 登录失败次数限制(5次失败后锁定账户10分钟)
   - 登录成功后生成JWT Token,存储到Cookie中

3. **会话管理**
   - Token有效期24小时
   - Token过期自动刷新机制
   - 会话超时自动登出(默认30分钟无操作)
   - 多点登录检测(同一账号多地登录,提示用户)

**验收标准**:
- [ ] 能够正确显示登录界面
- [ ] 输入正确用户名密码后能够成功登录
- [ ] 输入错误密码时显示错误提示
- [ ] 登录失败5次后账户被锁定
- [ ] 登录成功后跳转到Dashboard页面
- [ ] "记住我"功能正常工作
- [ ] Token过期后能够自动刷新
- [ ] 会话超时后自动登出

**页面原型**: 
```
┌─────────────────────────────────┐
│    多地区监控平台                │
│    请输入您的登录凭据            │
├─────────────────────────────────┤
│ 用户名: [_____________]          │
│ 密码:   [_____________] 👁      │
│ ☑ 记住我                        │
│                                  │
│      [   登   录   ]             │
└─────────────────────────────────┘
```

**交互说明**:
- 点击"记住我"复选框,下次打开页面自动填充用户名
- 点击"🁡"图标可查看或隐藏密码
- 点击登录按钮后,显示Loading动画,禁止重复提交
- 登录成功后显示成功提示,自动跳转到Dashboard
- 登录失败后在输入框下方显示错误提示

#### 3.2.2 用户登出

**功能描述**: 用户主动登出系统,清除客户端会话数据,使Token失效。

**用户故事**:
> 作为系统用户,我希望能够安全地退出系统,以保护我的账户安全。

**功能需求**:
1. **登出操作**
   - 点击顶部导航栏的"登出"按钮
   - 弹出确认对话框,询问是否确认登出
   - 确认后清除Cookie中的Token
   - 清除本地存储的用户信息
   - 调用后端登出接口,使服务端Token失效

2. **跳转处理**
   - 登出成功后跳转到登录页面
   - 清除浏览器历史记录(可选)
   - 显示登出成功提示

**验收标准**:
- [ ] 点击"登出"按钮弹出确认对话框
- [ ] 确认登出后清除Token和用户信息
- [ ] 登出成功后跳转到登录页面
- [ ] 登出后的Token无法继续访问API

#### 3.2.3 个人信息管理

#### 5.2.2 边缘节点管理规则

##### 5.2.2.1 边缘节点负载均衡策略

**1. 负载均衡算法**

系统采用加权最小连接数算法(Weighted Least Connections, WLC)进行摄像头分配:

**权重计算公式**:
```
Weight = (1 - 当前连接数/最大连接数) × 性能权重
```

**性能权重定义**:

| CPU使用率 | 权重系数 | 说明 |
|-----------|----------|------|
| < 50% | 1.0 | 节点负载低,优先分配 |
| 50% - 70% | 0.8 | 节点负载中等 |
| 70% - 85% | 0.6 | 节点负载较高,谨慎分配 |
| ≥ 85% | 0.3 | 节点负载高,尽量避免分配 |

**内存使用率调整因子**:

| 内存使用率 | 调整系数 | 说明 |
|-----------|----------|------|
| < 60% | 1.0 | 内存充足 |
| 60% - 80% | 0.9 | 内存使用较高 |
| ≥ 80% | 0.8 | 内存使用高 |

**综合权重计算**:
```
FinalWeight = Weight × 内存调整系数 × 地域优先级系数
```

**地域优先级系数**:

| 地域关系 | 系数 | 说明 |
|----------|------|------|
| 同一可用区 | 1.0 | 优先选择同一可用区的节点 |
| 同一城市 | 0.9 | 次优选择 |
| 跨城市 | 0.8 | 跨地域选择,网络延迟较高 |

**2. 节点选择策略**

摄像头分配到边缘节点时,按以下优先级顺序筛选:

**优先级1: 地域就近原则**
```
1. 同一区域 > 跨区域
2. 网络延迟 < 50ms > 网络延迟 50-100ms > 网络延迟 > 100ms
3. 同一可用区 > 跨可用区
```

**优先级2: 节点健康状态**
```
1. 在线节点 > 离线节点(不选择)
2. 正常节点 > 高负载节点(权重较低)
3. 负载低的节点 > 负载高的节点
```

**优先级3: 负载均衡原则**
```
1. 权重高的节点 > 权重低的节点
2. 当前连接数少的节点 > 连接数多的节点
3. 平均延迟低的节点 > 延迟高的节点
```

**优先级4: 业务优先级**
```
1. 重要摄像头 > 普通摄像头
2. 重要摄像头优先分配到高性能节点
3. 普通摄像头可以分配到低性能节点
```

**3. 节点选择流程**

```
用户添加摄像头或启动摄像头
    ↓
获取摄像头所属区域
    ↓
筛选同区域的在线节点
    ↓
如果同区域节点不足,筛选邻近区域节点
    ↓
计算各节点的综合权重
    ↓
选择权重最高的节点
    ↓
检查节点负载(连接数/性能)
    ↓
如果节点未过载,分配摄像头
    ↓
如果节点过载,选择次优节点
    ↓
完成分配
```

##### 5.2.2.2 边缘节点故障迁移策略

**1. 故障检测**

| 检测指标 | 检测方法 | 检测间隔 | 故障判定 |
|----------|----------|----------|----------|
| 心跳超时 | 心跳检测 | 30秒 | 60秒未收到心跳 |
| 服务不可达 | 健康检查接口 | 60秒 | 3次失败 |
| 资源过载 | CPU/内存监控 | 60秒 | CPU>95%或内存>95% |

**2. 故障等级**

| 故障等级 | 描述 | 影响范围 | 迁移策略 |
|----------|------|----------|----------|
| **轻微** | 节点高负载(CPU>85%或内存>85%) | 新摄像头不分配到该节点 | 负载均衡调整 |
| **严重** | 节点离线(心跳超时>60秒) | 该节点所有摄像头离线 | 立即迁移所有摄像头 |
| **紧急** | 节点完全不可达(网络故障) | 该节点所有摄像头不可达 | 立即迁移所有摄像头 |

**3. 故障迁移流程**

```
节点故障检测(心跳超时/健康检查失败)
    ↓
判断故障级别(轻微/严重/紧急)
    ↓
立即停止向故障节点分配新摄像头
    ↓
识别该节点上的所有摄像头
    ↓
按摄像头优先级排序(重要摄像头优先)
    ↓
选择最优的备用节点(综合权重计算)
    ↓
迁移摄像头到备用节点
    ↓
更新摄像头关联的边缘节点ID
    ↓
重新建立视频流连接
    ↓
记录迁移日志(摄像头、原节点、新节点、时间)
    ↓
通知管理员(邮件/系统告警)
    ↓
迁移完成
```

**4. 迁移优先级**

**摄像头优先级定义**:

| 优先级 | 摄像头类型 | 说明 | 迁移顺序 |
|--------|-----------|------|----------|
| **P0** | 关键摄像头 | 门口、安全重点区域 | 1-5分钟内迁移 |
| **P1** | 重要摄像头 | 营业区域、仓库区域 | 5-10分钟内迁移 |
| **P2** | 普通摄像头 | 一般监控区域 | 10-30分钟内迁移 |

**迁移并发控制**:
- 同时迁移的摄像头数量: 最多5个
- 单个摄像头迁移超时时间: 2分钟
- 迁移失败重试次数: 3次

**5. 迁移失败处理**

```
迁移失败原因:
1. 备用节点负载过高
2. 备用节点不可用
3. 摄像头连接失败
4. 网络故障

处理策略:
1. 记录迁移失败日志
2. 尝试选择其他备用节点
3. 如果所有备用节点都不可用,标记摄像头为"迁移待处理"
4. 5分钟后自动重试迁移
5. 3次重试失败后,告警通知管理员人工处理
```

**6. 节点恢复**

```
故障节点恢复上线
    ↓
系统检测到节点心跳恢复
    ↓
节点标记为"在线"状态
    ↓
评估节点负载情况
    ↓
如果节点负载正常,开始接收新摄像头
    ↓
可选: 迁移部分摄像头回到原节点(负载均衡)
    ↓
节点恢复正常
```

**节点恢复后的负载均衡策略**:
- 原则上不强制迁回原节点(避免频繁迁移)
- 如果原节点负载很低(<30%),可以迁回部分摄像头
- 迁回优先级: 先迁回离该节点物理位置最近的摄像头

##### 5.2.2.3 负载均衡配置

**1. 全局负载均衡参数**

| 参数名称 | 默认值 | 说明 |
|----------|--------|------|
| 最大连接数 | 100 | 每个节点的最大摄像头连接数 |
| 负载阈值 | 80% | CPU/内存负载告警阈值 |
| 高负载阈值 | 85% | CPU/内存高负载判定阈值 |
| 严重过载阈值 | 95% | CPU/内存严重过载判定阈值 |
| 心跳间隔 | 30秒 | 节点心跳发送间隔 |
| 心跳超时 | 60秒 | 节点离线判定超时 |
| 健康检查间隔 | 60秒 | 节点健康检查间隔 |

**2. 节点级负载均衡参数**

每个节点可以单独配置负载均衡参数:

| 参数名称 | 默认值 | 说明 |
|----------|--------|------|
| 节点优先级 | 中 | 节点分配优先级(高/中/低) |
| 最大连接数 | 100 | 该节点的最大摄像头连接数 |
| CPU告警阈值 | 80% | 该节点的CPU告警阈值 |
| 内存告警阈值 | 85% | 该节点的内存告警阈值 |
| 地域权重 | 1.0 | 该节点的地域权重系数 |

##### 5.2.2.4 边缘节点管理规则

1. **负载均衡**: 采用加权最小连接数算法,综合考虑CPU、内存、地域等因素
2. **健康检查**: 节点每30秒发送一次心跳
3. **离线判定**: 超过60秒未收到心跳判定为离线
4. **高负载判定**: CPU>80%或内存>85%判定为高负载
5. **故障迁移**: 节点离线时自动迁移摄像头到其他节点,按优先级顺序迁移
6. **负载均衡调整**: 节点负载过高时停止分配新摄像头到该节点

#### 5.2.3 视频流管理规则
1. **并发限制**: 每个用户最多同时观看16路视频
2. **会话超时**: 流会话30分钟无操作自动断开
3. **质量控制**: 根据网络带宽自适应调整码率
4. **断线重连**: WebRTC连接断开后自动重连,最多3次

#### 5.2.4 录像存储管理规则

##### 5.2.4.1 存储分级策略

根据录像的重要性和访问频率,采用三级存储策略:

| 存储级别 | 保留期限 | 存储介质 | 访问速度 | 成本 | 适用场景 |
|----------|----------|----------|----------|------|----------|
| **热数据** | 1-7天 | SSD本地存储 | 毫秒级 | 高 | 近期录像、告警录像、需频繁回放的录像 |
| **温数据** | 8-30天 | HDD本地存储 | 秒级 | 中 | 常规计划录像、手动录像 |
| **冷数据** | 31-180天 | 云存储/OSS | 分钟级 | 低 | 历史归档录像、合规保留录像 |

##### 5.2.4.2 存储空间管理

**1. 存储使用率监控**
- 实时监控存储空间使用率
- 按摄像头、按日期、按存储级别统计
- 提供存储使用趋势分析

**2. 预警阈值**
- **警告阈值**: 存储使用率达到80%时
  - 产生警告告警
  - 发送邮件通知管理员
  - 系统仪表盘显示警告提示

- **紧急阈值**: 存储使用率达到90%时
  - 产生严重告警
  - 发送邮件和消息推送通知
  - 执行自动清理策略:
    - 优先删除最老的冷数据(31-180天)
    - 降低非关键摄像头的录像质量
    - 缩短非重要摄像头的保留周期

- **扩容阈值**: 存储使用率达到95%时
  - 产生紧急告警
  - 立即通知管理员
  - 自动触发扩容流程(如果配置了自动扩容)

##### 5.2.4.3 录像完整性保障

**1. 录像校验**
- 校验频率: 每天凌晨2点自动校验
- 校验方法: MD5哈希校验
- 校验范围:
  - 当天新增的录像文件
  - 抽样校验历史录像(每天随机抽取5%)
- 校验结果:
  - 正常: 标记为已校验
  - 异常: 生成完整性告警

**2. 录像修复**
- 修复触发: 发现录像损坏时自动触发
- 修复策略:
  - 尝试从边缘节点拉取备份录像
  - 如果边缘节点也有损坏,标记为永久损坏
- 修复结果: 记录修复日志

**3. 录像备份**
- **关键录像多副本**:
  - 告警录像: 自动保存3副本(本地2份+云端1份)
  - 手动录像: 自动保存2副本
  - 计划录像: 单副本
- **备份策略**:
  - 本地备份: 热数据存储和温数据存储各保留一份
  - 云端备份: 关键录像自动上传到OSS

##### 5.2.4.4 灾难恢复策略

**1. 备份频率**
- **增量备份**: 每日凌晨3点执行增量备份
  - 备份当天新增和修改的录像
  - 备份时间约1-2小时(取决于数据量)
- **全量备份**: 每周日凌晨2点执行全量备份
  - 备份所有录像文件
  - 备份时间约4-8小时(取决于数据量)

**2. 备份保留**
- 保留最近30天的备份
- 自动删除超过30天的备份文件
- 每季度保留一个全量备份用于长期归档

**3. 异地备份** (可选功能)
- 云端OSS异地备份
- 自动同步录像到云端
- 支持手动触发备份

**4. 恢复演练**
- 演练频率: 每季度一次
- 演练内容:
  - 从备份恢复录像文件
  - 验证录像文件完整性
  - 测试录像回放功能
- 演练结果: 记录恢复演练报告

**5. RTO和RPO定义**
- **RTO (Recovery Time Objective)**: 恢复时间目标
  - 单个录像文件恢复: <10分钟
  - 批量录像恢复: <2小时
  - 完整系统恢复: <4小时
- **RPO (Recovery Point Objective)**: 恢复点目标
  - 最大可接受的数据丢失时间: 1小时

##### 5.2.4.5 录像归档策略

**1. 自动归档**
- **归档触发条件**:
  - 录像文件年龄>30天
  - 录像类型为计划录像
  - 未标记为关键录像
- **归档操作**:
  - 将录像从温存储迁移到冷存储
  - 压缩录像文件(可选,H.264→H.265)
  - 更新录像元数据中的存储级别标记
- **归档时间**: 每天凌晨4点执行

**2. 归档索引**
- 建立归档录像的快速检索索引
- 索引字段: 摄像头ID、时间范围、录像类型、关键字
- 索引存储: Redis缓存+持久化数据库
- 索引更新: 归档操作完成后自动更新索引

**3. 归档检索**
- 检索性能要求: <10秒返回结果
- 检索流程:
  1. 从索引查询录像位置
  2. 如果是冷存储,触发数据回热
  3. 数据回热后返回录像文件路径
- 数据回热时间: 取决于文件大小,通常5-30分钟

**4. 手动归档**
- 支持用户手动选择录像进行归档
- 支持标记录像为永久保留(不自动归档)
- 支持取消归档(将录像从冷存储恢复到温存储)

##### 5.2.4.6 录像管理规则

1. **录像周期**: 默认为24小时,可根据配置调整
2. **存储策略**: 录像文件按日期分目录存储,采用三级存储策略
3. **清理策略**: 超过保留期(默认30天)的录像自动归档或删除
4. **告警录像**: 触发告警时自动开始录像,持续5分钟,并保存为关键录像
5. **完整性保障**: 每天自动校验录像完整性,发现损坏自动修复

#### 5.2.5 用户权限规则
1. **权限继承**: 子区域继承父区域的权限
2. **资源隔离**: 不同区域的资源相互隔离
3. **操作审计**: 所有关键操作记录日志

### 7.3 高可用架构

#### 7.3.1 组件高可用设计

系统核心组件均采用高可用设计,确保单一故障不影响整体服务:

| 组件 | 高可用方案 | 故障切换时间 | 数据一致性 | 说明 |
|------|-----------|-------------|-----------|------|
| **Nginx** | Keepalived + 双机热备 | <1秒 | 无状态,无需同步 | 使用虚拟IP实现自动切换 |
| **MySQL** | MGR多主集群 | <30秒 | 半同步复制 | 1主2从,自动故障转移 |
| **Redis** | Redis Sentinel | <5秒 | 异步复制,可能丢少量数据 | 1主2从+哨兵集群 |
| **Kafka** | 多副本机制 | <1秒 | 副本同步 | 3个Broker,每个分区3副本 |
| **Janus Gateway** | 多实例负载均衡 | <3秒 | 无状态 | 多实例部署,Nginx分发 |
| **后端服务** | 微服务集群 | <10秒 | 无状态 | 水平扩展,自动扩容 |

#### 7.3.2 故障检测与恢复

**1. 故障检测机制**

| 检测对象 | 检测方式 | 检测间隔 | 超时判定 |
|----------|----------|----------|----------|
| Nginx | 心跳检测 | 5秒 | 3次失败 |
| MySQL | MGR健康检查 | 10秒 | 主库无响应 |
| Redis | Sentinel检测 | 5秒 | 主库下线 |
| Kafka | Broker心跳 | 5秒 | Broker不可达 |
| Janus Gateway | 健康检查接口 | 30秒 | 接口无响应 |
| 后端服务 | 健康检查接口 | 30秒 | 接口无响应 |

**2. 故障判断级别**

- **P0级故障**: 服务完全不可用,影响所有用户
  - 处理时间: 立即
  - 通知方式: 电话+短信+系统告警
  - 自动切换: 是

- **P1级故障**: 服务部分不可用,影响部分用户
  - 处理时间: 5分钟内
  - 通知方式: 系统告警+邮件
  - 自动切换: 是

- **P2级故障**: 服务性能下降,但不影响核心功能
  - 处理时间: 30分钟内
  - 通知方式: 系统告警
  - 自动切换: 否,人工处理

**3. 故障恢复流程**

```
故障检测(心跳机制/健康检查)
    ↓
判断故障级别(P0/P1/P2)
    ↓
执行故障切换策略(自动/手动)
    ↓
通知相关系统(负载均衡器、缓存等)
    ↓
记录故障日志(故障时间、原因、处理方式)
    ↓
通知运维人员(根据故障级别)
    ↓
故障修复
    ↓
服务验证
    ↓
恢复完成
```

**4. 故障恢复时间要求**

| 故障类型 | 目标RTO | 目标RPO | 说明 |
|----------|---------|---------|------|
| Nginx故障 | <1分钟 | 0 | 无状态服务,立即切换 |
| MySQL故障 | <15分钟 | <5分钟 | MGR自动切换,可能有少量数据丢失 |
| Redis故障 | <5分钟 | <5分钟 | Sentinel自动切换,可能有少量数据丢失 |
| Kafka故障 | <2分钟 | <1分钟 | 副本自动接管 |
| 后端服务故障 | <10分钟 | 0 | 无状态服务,立即切换 |
| 磁盘故障 | <30分钟 | <1小时 | 硬件更换+数据恢复 |

#### 7.3.3 跨可用区部署

为了进一步提高系统的可用性,建议采用跨可用区部署:

**主可用区(AZ-A)**:
- 2个Nginx实例(主备)
- 1个MySQL主节点
- 1个MySQL从节点
- 1个Redis主节点
- 1个Redis从节点
- 2个Kafka Broker
- 2个Janus Gateway实例
- 2个后端服务实例

**备可用区(AZ-B)**:
- 1个MySQL从节点(只读)
- 1个Redis从节点(只读)
- 1个Kafka Broker
- 1个Janus Gateway实例
- 1个后端服务实例

**数据同步**:
- MySQL: MGR多主集群,主备之间异步复制
- Redis: 主从复制,主节点写入,从节点同步
- Kafka: 副本机制,跨可用区同步
- 录像数据: 定期备份到异地OSS

**故障切换**:
- 主可用区完全不可用时:
  - 负载均衡器自动切换到备可用区
  - 数据库只读模式,接受读请求
  - 视频流降级为单路播放
  - 管理员收到紧急告警

#### 7.3.4 灾难恢复方案

**1. 灾难场景定义**

| 灾难级别 | 场景描述 | 影响范围 | 恢复时间 |
|----------|----------|----------|----------|
| **L1** | 单个服务实例故障 | 部分功能 | <10分钟 |
| **L2** | 整个可用区故障 | 主要功能降级 | <2小时 |
| **L3** | 数据中心故障 | 完全不可用 | <4小时 |

**2. 灾难恢复策略**

**L1级灾难(单个实例故障)**:
- 检测: 健康检查失败
- 响应: 自动故障切换
- 恢复: 启动新实例,负载均衡器重新分发流量
- 恢复时间: <10分钟

**L2级灾难(整个可用区故障)**:
- 检测: 整个可用区心跳超时
- 响应:
  - 负载均衡器切换到备用可用区
  - 数据库切换为只读模式
  - 视频流降级功能
- 恢复:
  - 修复主可用区问题
  - 数据从备可用区同步回主可用区
  - 逐步恢复服务
- 恢复时间: <2小时

**L3级灾难(数据中心故障)**:
- 检测: 整个数据中心不可达
- 响应:
  - 切换到异地灾备中心
  - 启动灾备系统
  - DNS切换到灾备IP
- 恢复:
  - 修复数据中心问题
  - 数据从灾备中心回迁
  - 完整恢复服务
- 恢复时间: <4小时

**3. 灾难恢复演练**

- 演练频率: 每半年一次
- 演练类型:
  - 模拟L1级灾难(随机关闭一个实例)
  - 模拟L2级灾难(模拟可用区故障)
  - 模拟L3级灾难(模拟数据中心故障)
- 演练内容:
  - 故障检测和切换时间
  - 数据完整性验证
  - 服务恢复功能验证
- 演练报告: 记录演练过程、问题、改进措施

**4. 备份数据恢复**

**恢复流程**:
1. 确定需要恢复的数据范围(时间范围、摄像头等)
2. 选择最近的备份点
3. 停止相关服务
4. 恢复数据文件
5. 验证数据完整性
6. 启动服务
7. 验证服务功能

**恢复时间**:
- 单个录像文件: <10分钟
- 批量录像(100个文件): <2小时
- 全量数据恢复: <4小时

## 8. 接口规范

### 8.1 接口设计原则

1. **RESTful风格**: 使用REST风格的API设计
2. **统一响应格式**: 所有接口返回统一的数据格式
3. **版本控制**: URL中包含版本号(/api/v1/)
4. **错误处理**: 统一的错误码和错误信息
5. **认证授权**: JWT Token认证,基于角色的授权

### 8.2 通用响应格式

```json
{
  "code": 200,
  "message": "success",

  "timestamp": "2026-02-08T10:30:00Z"
```

```json
  "message": "请求参数错误",
```

#### 13.5.3 数据脱敏

- **数据遮蔽**: 敏感信息(如密码、身份证号)遮蔽显示
- **日志脱敏**: 日志中不记录敏感信息
